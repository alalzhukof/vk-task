# SecureDesk на Go

Учебный сервис заявок для промежуточной защиты по безопасности вычислительных систем. Пользователь создаёт обращения и обсуждает их с назначенным оператором. Оператор видит свои и назначенные заявки, отвечает и меняет статус. Администратор управляет ролями и назначением операторов. Отдельный worker доставляет события через RabbitMQ и записывает аудит.

## Запуск

API, обработчик очереди и их тесты написаны на **Go**. Служебные команды также написаны на Go и запускаются в контейнере.

Нужен только Docker Desktop или Docker Engine с Compose v2. Go, Python, Node.js и Make на ноутбуке не требуются. Рекомендуется выделить Docker 4 CPU, 6 ГБ памяти и 10 ГБ диска с учётом образа браузерных тестов. Первое скачивание образов требует Интернета.

```sh
docker compose up -d --build --wait
```

Откройте **http://localhost:8080**. Создайте свой аккаунт: имя из латинских букв, цифр и `_`, пароль от 12 символов. При первом запуске контейнер `init` создаёт уникальные секреты в постоянных Docker-томах. Контейнер `db-sync` включает синхронную репликацию, обновляет схему и создаёт первого администратора до запуска API. Повторный запуск сохраняет данные и секреты.

Вход администратора: `securedesk_admin`. Его случайный пароль можно получить командой:

```sh
docker compose --profile tools run --build --rm tools admin-credentials
```

В блоке «Команда и роли» назначьте зарегистрированному аккаунту роль оператора. Откройте обсуждение заявки, выберите оператора и сохраните.

Контейнеры `init` и `db-sync` после подготовки имеют состояние `Exited (0)` — это нормальное успешное завершение. Остальные сервисы продолжают работать.

Не заменяйте `localhost` на IP: проверка Origin настроена на `http://localhost:8080`.

Машиночитаемый контракт API: `http://localhost:8080/api/openapi.json`. Интерфейс приложения не требует CDN или внешних JavaScript-библиотек.

## Проверки

```sh
docker compose --profile test run --build --rm unit
docker compose --profile test run --build --rm tests
docker compose --profile test run --build --rm browser
docker compose --profile tools run --build --rm tools firewall
docker compose --profile tools run --build --rm tools rabbit-failover
docker compose --profile tools run --build --rm tools backup
docker compose --profile tools run --build --rm tools restore --file backups/ИМЯ_КОПИИ.dump
docker compose --profile tools run --build --rm tools pg-failover
```

Последняя команда определяет действующий primary, аварийно останавливает его, повышает реплику до primary и проверяет сохранность заявки и новые записи. Это **управляемое переключение оператором**, а не автоматические выборы лидера БД. Не запускайте старый primary вручную: сначала выполните `docker compose --profile tools run --build --rm tools rejoin`, чтобы исключить два независимых primary. Эта команда возвращает остановленный узел как реплику с помощью pg_rewind.

Тесты создают отдельные учетные записи и заявки в локальной учебной БД. Проверки отказов меняют состояние только Compose-проекта `securedesk`. Не запускайте их одновременно с защитой или друг с другом. Новые результаты проверок сохраняются в `evidence/`; исходный архив не содержит ранее накопленных результатов или пользовательских данных.

## Состав

| Компонент | Назначение |
| --- | --- |
| init / db-sync | Однократная подготовка секретов и синхронной репликации при запуске |
| front | Nginx, статический интерфейс, HTTP reverse proxy |
| api | Go net/http, сессии, роли, заявки, назначение, комментарии, кеш |
| worker | Публикация outbox, подтверждения брокера, идемпотентный аудит |
| pg-primary / pg-standby | PostgreSQL 17, потоковая синхронная репликация автоматически при запуске |
| redis | Кеш списков заявок, ограничение попыток входа |
| rabbit1 / rabbit2 / rabbit3 | Кластер RabbitMQ, очередь quorum с тремя участниками |
| api-net / worker-net | Сетевые пространства с правилами iptables, default deny |

API и worker используют отдельные роли PostgreSQL с ограниченными правами. Они совместно используют одну логическую БД в учебном стенде, но имеют разные обязанности и независимо запускаемые процессы. Это осознанное упрощение, а не полная автономность хранения каждого микросервиса.

## Структура исходного кода

- `cmd/` — API, worker, инициализация, проверки и служебные команды на Go.
- `internal/` — реализация, миграция схемы и автоматические тесты.
- `db/` — PostgreSQL, базовая схема и репликация.
- `infra/` — Nginx, RabbitMQ, firewall и окружение браузерных тестов.
- `web/` — интерфейс приложения.
- `scripts/` — браузерный сценарий проверки.
- `docs/openapi.json` — контракт API, включаемый в образ приложения.
- `compose.yaml` и `Dockerfile` — сборка и запуск всего стенда.

## Границы стенда

Внешний порт опубликован только на loopback ноутбука. HTTP допустим здесь для локальной демонстрации. Для размещения в Интернете нужны HTTPS, `COOKIE_SECURE=true`, корректный `APP_ORIGIN`, управление секретами и дополнительное усиление инфраструктуры. Внутренний трафик этого стенда не зашифрован. Владение Docker даёт административный доступ к данным и секретам.

Реплика и три брокера находятся на одном физическом ноутбуке. Они защищают от отказа отдельных процессов/контейнеров, но не от отказа ноутбука. Redis и API не дублируются. Потеря кеша не теряет заявки, однако вход намеренно возвращает 503 без доступного ограничителя попыток. Синхронная БД блокирует подтверждение новых записей при потере standby: это выбор сохранности данных в ущерб доступности.

## Остановка

```sh
docker compose stop
```

Тома сохраняются. `docker compose down -v` удалит данные, поэтому эта команда не входит в обычные сценарии.
